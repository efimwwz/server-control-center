# Установка и удалённый доступ

Это руководство объясняет, как установить Server Control Center (SCC), что означает localhost и как безопасно открывать панель через SSH, Nginx или Caddy.

[Руководство на английском](INSTALL.md) · [Описание проекта](README.ru.md)

---

## 1. Выберите способ доступа к панели

Есть три распространённых варианта:

| Вариант | Для кого подходит | Публичные порты |
|---|---|---|
| SSH-туннель | Один администратор; домен и публичный веб-доступ не нужны | Только SSH; порт SCC не открывается |
| Обратный прокси Nginx | На сервере уже работает Nginx или вы предпочитаете его | TCP 80 и 443 |
| Обратный прокси Caddy | Новая или простая установка с автоматическим HTTPS | TCP 80 и 443 |

Nginx и Caddy — альтернативы для входящего веб-трафика. Не пытайтесь одновременно заставить их слушать одни и те же публичные порты 80 и 443. Если Nginx уже обслуживает ваши сайты, добавьте SCC в его конфигурацию. Если сайты уже обслуживает Caddy, добавьте SCC в Caddyfile.

Можно использовать и другой обратный прокси. Он должен передавать весь сайт SCC на http://127.0.0.1:3000 и требовать авторизацию до предоставления доступа.

## 2. Что такое localhost, IP-адрес и порт

Это самый важный раздел для тех, кто впервые устанавливает серверные приложения.

### Что означает localhost?

localhost означает **этот же самый компьютер**.

- 127.0.0.1 — IPv4-адрес локального интерфейса.
- ::1 — IPv6-адрес локального интерфейса.
- Запросы на эти адреса остаются внутри текущего компьютера и не уходят в публичный интернет.

Частая ошибка: localhost в браузере на вашем ноутбуке — это **ноутбук**, а не VPS. Когда вы открываете http://127.0.0.1:3000 на ноутбуке, браузер пытается подключиться к порту 3000 самого ноутбука.

SCC публикует порт 127.0.0.1:3000 на **сервере**. Поэтому:

- Программа, запущенная на VPS, может обращаться к панели по адресу http://127.0.0.1:3000.
- Nginx или Caddy на этом же VPS также могут обращаться к панели по адресу http://127.0.0.1:3000.
- Другой компьютер в интернете не может напрямую подключиться к порту 3000 сервера.

### Что такое 0.0.0.0 и почему приложение его использует?

Внутри Docker-контейнера приложение Node.js слушает адрес 0.0.0.0:3000. Это означает, что оно принимает соединения на сетевых интерфейсах самого контейнера.

Это **не означает**, что приложение открыто всему интернету. Docker публикует порт контейнера на сервере следующим образом:

~~~yaml
ports:
  - "127.0.0.1:3000:3000"
~~~

Левая часть — адрес и порт на сервере, правая — порт внутри контейнера. Привязка на стороне сервера ограничена локальным интерфейсом. Не меняйте её на 0.0.0.0:3000:3000.

### Какие порты используются

| Порт | Для чего нужен | Должен быть открыт в интернет? |
|---|---|---|
| 22/tcp (или ваш SSH-порт) | Управление сервером и SSH-туннели | Только если используете SSH; по возможности ограничьте адреса источников |
| 80/tcp | HTTP и проверка сертификата/перенаправление для Nginx или Caddy | Да, при публичном домене и HTTP-проверке сертификата |
| 443/tcp | HTTPS-соединение браузера с Nginx или Caddy | Да, при публичном HTTPS-домене |
| 3000/tcp | Веб-приложение SCC на локальном интерфейсе сервера | **Нет** |
| 8099/tcp | Локальный Nginx stub_status для метрик SCC, создаваемый при установке, если Nginx уже активен | **Нет** |

Порт 8099 — это не адрес веб-панели. Это отдельный локальный endpoint, через который host-agent считывает статистику Nginx.

### Как соединяются компоненты

При доступе через домен схема выглядит так:

~~~text
Ваш браузер
    |
    | HTTPS, TCP 443
    v
scc.example.com (DNS указывает на ваш VPS)
    |
    v
Nginx или Caddy
    | TLS-сертификат
    | проверка логина и пароля
    |
    | HTTP по локальному интерфейсу
    v
127.0.0.1:3000
    |
    v
Веб-контейнер SCC
    |
    | read-only подключение сокета агента
    v
/run/scc-agent/agent.sock
    |
    v
Host-agent SCC (systemd, root)
    |
    v
Показатели сервера и сведения о Docker
~~~

HTTPS защищает соединение от браузера до обратного прокси. Затем прокси обращается к SCC по локальному интерфейсу того же VPS.

## 3. Подготовка сервера

### Требования

- Ubuntu 24.04 LTS.
- Архитектура amd64 или arm64.
- systemd и пакетный менеджер apt.
- Права root или пользователь с sudo.
- Свободный TCP-порт 3000 на сервере.
- Исходящий HTTPS-доступ к GitHub и GHCR.
- Если Docker ещё не установлен — доступ к официальному репозиторию Docker.

Установщик SCC может установить Docker Engine, если он отсутствует и не обнаружены конфликтующие компоненты Docker/containerd/runc. Если Docker уже установлен, но остановлен, установщик остановится и попросит запустить его самостоятельно. Он не должен перезапускать существующий Docker daemon или посторонние контейнеры.

### Если хотите открывать панель по домену

Выберите домен или поддомен, например scc.example.com. До получения публичного TLS-сертификата:

1. Создайте DNS-запись A для scc.example.com, указывающую на публичный IPv4 вашего сервера.
2. Создавайте запись AAAA только в том случае, если на VPS действительно работает публичный IPv6 и firewall разрешает входящие соединения по IPv6.
3. Убедитесь, что TCP-порты 80 и 443 доступны снаружи и направлены на этот VPS.
4. Проверьте firewall самого сервера и сетевой firewall/группы безопасности у хостинг-провайдера.

Не открывайте порты 3000 и 8099.

Если используете UFW, сначала убедитесь, что правило SSH разрешено, иначе можно потерять удалённый доступ. Например:

~~~bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status
~~~

Не включайте UFW удалённо, пока не проверили, что ваш SSH-порт разрешён и у вас есть способ восстановить доступ через панель хостинг-провайдера.

## 4. Установка SCC

Установщик одной командой станет доступен после публичной публикации репозитория, архива GitHub Release и образа GHCR. До этого команда приведена как пример и не сможет завершить установку.

~~~bash
curl -fsSL https://raw.githubusercontent.com/efimwwz/server-control-center/main/install.sh | sudo bash
~~~

Установка конкретной версии:

~~~bash
curl -fsSL https://raw.githubusercontent.com/efimwwz/server-control-center/main/install.sh | sudo env SCC_VERSION=1.1.1 bash
~~~

Если хотите сначала посмотреть скрипт:

~~~bash
curl -fsSLo /tmp/scc-install.sh https://raw.githubusercontent.com/efimwwz/server-control-center/main/install.sh
less /tmp/scc-install.sh
sudo bash /tmp/scc-install.sh
~~~

Установщик проверяет Ubuntu, архитектуру, порт 3000 и существующие ресурсы SCC; проверяет конфликтующие компоненты контейнерной среды; скачивает архив релиза и проверяет SHA256; устанавливает службу host-agent; скачивает готовый образ SCC из GHCR; запускает только контейнер SCC и проверяет его состояние.

Установщику не нужен n8n и не требуется доступ к инфраструктуре автора проекта.

### Если Nginx уже установлен

Если Nginx активен во время установки SCC, установщик добавляет отдельную конфигурацию:

/etc/nginx/conf.d/scc-nginx-status.conf

Она слушает только 127.0.0.1:8099 и предоставляет путь /nginx_status для агента SCC. Существующие сайты Nginx не заменяются.

Этот endpoint нужен для сбора статистики Nginx и не является конфигурацией обратного прокси для веб-панели. Не открывайте порт 8099 в публичном firewall.

## 5. Вариант A — SSH-туннель (Nginx и Caddy не нужны)

Это самый простой и безопасный способ, если панелью пользуется один администратор.

На своём компьютере откройте терминал и выполните:

~~~bash
ssh -N -L 3000:127.0.0.1:3000 USER@SERVER_IP
~~~

Замените USER на имя пользователя SSH на вашем VPS, а SERVER_IP — на публичный IP-адрес или SSH-имя сервера.

Не закрывайте это окно терминала. Затем откройте в браузере **на своём компьютере**:

http://127.0.0.1:3000

SSH-туннель перенаправляет локальный порт 3000 ноутбука через SSH на 127.0.0.1:3000 VPS. Публичный порт SCC и домен для этого не нужны.

Если порт 3000 на ноутбуке уже занят, используйте другой локальный порт:

~~~bash
ssh -N -L 13000:127.0.0.1:3000 USER@SERVER_IP
~~~

Тогда на ноутбуке откройте http://127.0.0.1:13000.

## 6. Вариант B — Nginx с HTTPS и паролем

Используйте этот вариант, если Nginx уже работает на VPS или вы предпочитаете Nginx.

### Шаг 1. Установите Nginx или проверьте текущую установку

Если Nginx уже обслуживает другие сайты, не переустанавливайте его. Добавьте SCC как ещё один виртуальный хост в существующий экземпляр Nginx.

Если Nginx ещё не установлен:

~~~bash
sudo apt update
sudo apt install -y nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx
~~~

### Шаг 2. Создайте виртуальный хост

Создайте новый файл конфигурации:

~~~bash
sudo nano /etc/nginx/sites-available/scc.example.com
~~~

Сначала используйте HTTP-конфигурацию. Замените scc.example.com на свой домен:

~~~nginx
server {
    listen 80;
    listen [::]:80;
    server_name scc.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }
}
~~~

Включите сайт и проверьте конфигурацию:

~~~bash
sudo ln -s /etc/nginx/sites-available/scc.example.com /etc/nginx/sites-enabled/scc.example.com
sudo nginx -t
sudo systemctl reload nginx
~~~

Если символическая ссылка уже существует, не создавайте её повторно. Если Nginx сообщает о дублирующемся server_name, сначала проверьте существующие виртуальные хосты и не удаляйте их вслепую.

### Шаг 3. Получите HTTPS-сертификат

DNS-запись должна указывать на этот VPS, а сервер должен быть доступен из интернета по TCP-порту 80. И firewall сервера, и firewall провайдера должны пропускать проверочный запрос.

Ниже приведён рекомендуемый способ установки Certbot через Snap для Ubuntu. Если Certbot уже установлен, сначала проверьте источник установки, чтобы не создавать две конкурирующие версии.

~~~bash
sudo apt update
sudo apt install -y snapd
sudo snap install --classic certbot
~~~

Сделайте команду Certbot доступной в стандартном пути. Если файл уже существует, проверьте его, а не перезаписывайте:

~~~bash
sudo ln -s /snap/bin/certbot /usr/local/bin/certbot
~~~

Запросите и установите сертификат:

~~~bash
sudo certbot --nginx -d scc.example.com
~~~

Следуйте подсказкам. При выборе перенаправления выберите переход с HTTP на HTTPS. Certbot изменит конфигурацию Nginx, добавив сертификат.

Проверьте автоматическое продление:

~~~bash
sudo certbot renew --dry-run
~~~

### Шаг 4. Добавьте защиту паролем

В SCC нет собственной страницы входа. Добавим авторизацию на уровне Nginx.

Установите утилиту для файла паролей:

~~~bash
sudo apt install -y apache2-utils
~~~

Создайте пользователя и пароль. Команда запросит пароль:

~~~bash
sudo htpasswd -cB /etc/nginx/.htpasswd-scc sccadmin
~~~

Ключ -c используйте только при первом создании файла. Чтобы добавить ещё одного пользователя позже, запускайте htpasswd без ключа -c.

В Ubuntu Nginx обычно работает от имени www-data. Установите права, позволяющие Nginx читать файл паролей:

~~~bash
sudo chown root:www-data /etc/nginx/.htpasswd-scc
sudo chmod 640 /etc/nginx/.htpasswd-scc
~~~

Откройте конфигурацию Nginx, которую создал Certbot. В HTTPS-блоке server для scc.example.com добавьте две директивы внутрь блока location /:

~~~nginx
auth_basic "Server Control Center";
auth_basic_user_file /etc/nginx/.htpasswd-scc;
~~~

Итоговый HTTPS-блок location / должен выглядеть примерно так:

~~~nginx
location / {
    auth_basic "Server Control Center";
    auth_basic_user_file /etc/nginx/.htpasswd-scc;

    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_connect_timeout 5s;
    proxy_read_timeout 60s;
}
~~~

Сохраните директивы сертификата и перенаправление HTTP на HTTPS, которые создал Certbot. Не заменяйте ими всю конфигурацию Certbot.

Проверьте и перечитайте конфигурацию:

~~~bash
sudo nginx -t
sudo systemctl reload nginx
~~~

### Шаг 5. Сообщите SCC, что перед ним доверенный прокси

Откройте файл переменных приложения:

~~~bash
sudo nano /opt/server-control-center/.env
~~~

Укажите:

~~~ini
TRUST_PROXY=1
~~~

Остальные переменные SCC_VERSION, METRICS_PROVIDER и GEMINI_API_KEY оставьте без изменений.

Пересоздайте только контейнер SCC, чтобы новая переменная применилась:

~~~bash
sudo docker compose --project-directory /opt/server-control-center -f /opt/server-control-center/docker-compose.yml up -d --no-deps --force-recreate server-control-center
~~~

TRUST_PROXY=1 подходит, когда единственным путём к приложению является один доверенный обратный прокси. Не включайте параметр, если пользователи могут обходить прокси и напрямую обращаться к приложению.

### Шаг 6. Проверьте доступ через Nginx

Откройте:

https://scc.example.com

Браузер должен запросить логин и пароль. Запрос без авторизации должен возвращать HTTP 401, а не содержимое панели.

Внутренний endpoint на VPS должен продолжать работать:

~~~bash
curl -fsS http://127.0.0.1:3000/api/health
~~~

## 7. Вариант C — Caddy с автоматическим HTTPS

Caddy часто проще для новой установки: при правильных настройках DNS и сети он автоматически получает и продлевает публичные TLS-сертификаты.

Используйте Caddy, если именно он будет занимать порты 80 и 443. Другой веб-сервер не должен одновременно занимать те же публичные порты.

### Шаг 1. Установите Caddy из официального репозитория Ubuntu

~~~bash
sudo apt install --yes debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo chmod o+r /usr/share/keyrings/caddy-stable-archive-keyring.gpg
sudo chmod o+r /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install caddy
~~~

Официальный пакет устанавливает Caddy как службу systemd и автоматически запускает её.

Если Nginx уже слушает порты 80 и 443, не устанавливайте Caddy в расчёте, что оба сервиса смогут занять те же порты. Выберите один публичный обратный прокси или отдельно спланируйте более сложную схему.

### Шаг 2. Создайте хеш пароля

Выполните:

~~~bash
sudo caddy hash-password --algorithm argon2id
~~~

Caddy запросит пароль и не будет отображать его символы, если команда запущена в терминале. Скопируйте полученный хеш. Не записывайте обычный пароль в Caddyfile.

### Шаг 3. Настройте Caddyfile

Откройте:

~~~bash
sudo nano /etc/caddy/Caddyfile
~~~

Добавьте блок сайта. Замените домен и пример хеша на свой домен и хеш, созданный на предыдущем шаге:

~~~caddyfile
scc.example.com {
    basic_auth argon2id {
        sccadmin REPLACE_WITH_THE_GENERATED_HASH
    }

    reverse_proxy 127.0.0.1:3000
}
~~~

Caddy автоматически получает и продлевает публичный сертификат для публичного DNS-имени. Он также перенаправляет HTTP на HTTPS. Для этого DNS-запись должна указывать на VPS, а TCP-порты 80 и 443 должны быть доступны из интернета.

Caddy автоматически передаёт исходный Host и стандартные заголовки X-Forwarded. По умолчанию он игнорирует недоверенные входящие значения X-Forwarded, если доверенные прокси отдельно не настроены.

### Шаг 4. Проверьте конфигурацию и перезагрузите Caddy

~~~bash
sudo caddy fmt --overwrite /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
sudo systemctl status caddy
~~~

Если перезагрузка завершилась ошибкой, посмотрите журнал службы:

~~~bash
sudo journalctl -u caddy -n 100 --no-pager
~~~

### Шаг 5. Включите доверенный прокси в SCC

Откройте:

~~~bash
sudo nano /opt/server-control-center/.env
~~~

Укажите:

~~~ini
TRUST_PROXY=1
~~~

Пересоздайте только контейнер SCC:

~~~bash
sudo docker compose --project-directory /opt/server-control-center -f /opt/server-control-center/docker-compose.yml up -d --no-deps --force-recreate server-control-center
~~~

Теперь Caddy является внешней точкой входа. SCC по-прежнему доступен только на 127.0.0.1:3000.

### Шаг 6. Проверьте доступ через Caddy

Откройте https://scc.example.com. Браузер должен установить HTTPS-соединение и запросить настроенные логин и пароль.

Проверьте состояние Caddy и локального приложения:

~~~bash
sudo systemctl status caddy
curl -fsS http://127.0.0.1:3000/api/health
~~~

### Что делать, если домен не публичный?

Caddy может обслуживать локальные имена, например localhost, используя собственный локальный центр сертификации. Это не то же самое, что публичный сертификат Let's Encrypt: другие устройства не будут автоматически доверять локальному сертификату, пока вы не установите корневой сертификат на этих устройствах.

Для удалённого доступа через интернет используйте настоящее DNS-имя и публично доверенный сертификат.

## 8. Другие обратные прокси и URL с путём

Можно использовать другой обратный прокси, например Traefik, HAProxy или шлюз с централизованной авторизацией, если он передаёт весь сайт SCC на http://127.0.0.1:3000 и требует авторизацию.

Используйте отдельный поддомен, например scc.example.com. Не рассчитывайте, что панель заработает по вложенному пути example.com/scc/: текущая frontend-сборка рассчитана на корневой URL, отдельная настройка базового пути не предусмотрена.

Для любого обратного прокси:

- Сохраняйте привязку Docker-порта на 127.0.0.1:3000.
- Не открывайте порты 3000 и 8099 публично.
- Требуйте авторизацию до передачи запросов в SCC.
- Передавайте исходный Host, адрес клиента и протокол в заголовках.
- Включайте TRUST_PROXY=1 только тогда, когда к приложению можно обратиться исключительно через настроенный доверенный прокси.

## 9. Устранение неполадок

| Симптом | Возможная причина или проверка |
|---|---|
| http://127.0.0.1:3000 работает на VPS, но не открывается на ноутбуке | Это ожидаемо без SSH-туннеля или обратного прокси. localhost ноутбука — не VPS |
| Домен не открывается | Проверьте DNS A/AAAA, firewall провайдера, UFW и прослушивание портов 80/443 прокси-сервером |
| Caddy не получает сертификат | Проверьте публичный DNS и доступность TCP 80/443; посмотрите journalctl -u caddy |
| Certbot не проходит проверку | Убедитесь, что домен указывает на этот сервер и порт 80 доступен во время проверки |
| Nginx возвращает 502 Bad Gateway | Проверьте контейнер SCC и выполните curl http://127.0.0.1:3000/api/health на VPS |
| Браузер постоянно запрашивает пароль | Это ожидаемо при Basic Auth. Проверьте имя пользователя, файл паролей и журналы прокси |
| Панель открывается, но метрики не загружаются | Проверьте systemctl status scc-agent и docker logs server-control-center |
| Статистика Nginx недоступна | Проверьте локальный endpoint 127.0.0.1:8099/nginx_status; не открывайте порт 8099 в интернет |

Полезные команды SCC:

~~~bash
sudo docker compose --project-directory /opt/server-control-center -f /opt/server-control-center/docker-compose.yml ps
sudo docker compose --project-directory /opt/server-control-center -f /opt/server-control-center/docker-compose.yml logs --tail 100
sudo systemctl status scc-agent.service
curl -fsS http://127.0.0.1:3000/api/health
~~~

## 10. Обработка данных и приватность AI

Host-agent считывает системные показатели, сведения о Docker, службы и выбранные журналы. Кроме того, он обращается к api.ipify.org для определения внешнего IPv4-адреса (результат кэшируется пять минут) и отправляет ICMP-запросы на 1.1.1.1 для измерения задержки и потерь пакетов.

Без API-ключа Gemini AI-помощник использует локальный диагностический механизм. Если GEMINI_API_KEY настроен и пользователь задаёт вопрос AI-помощнику, вопрос, выбранные метрики и часть последних журналов отправляются Google Gemini.

Журналы могут содержать IP-адреса, имена хостов, URL, пути запросов, имена служб/контейнеров и идентификаторы. Маскирование скрывает только некоторые секреты в query-параметрах. Оно не гарантирует удаление каждого пароля, токена или персональной информации. Перед включением AI оцените, какие данные будут передаваться.

## 11. Удаление SCC

~~~bash
sudo bash /opt/server-control-center/deploy/uninstall.sh
~~~

Удалитель потребует точную фразу REMOVE SERVER CONTROL CENTER и создаст защищённую резервную копию в /var/backups/server-control-center. Он удаляет контейнер, файлы SCC и host-agent. Docker Engine и образы остаются; посторонние контейнеры не останавливаются.

Nginx/Caddy и конфигурации их сайтов удалитель SCC не удаляет. Если панель больше не нужна, удалите виртуальный хост SCC из конфигурации обратного прокси вручную.
